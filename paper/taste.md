# What the author's feedback teaches

Rules learned from the author's comments on drafts in this project. Read before writing or revising,
together with the global taste (`taste show` prints both). One rule per bullet, ending with the occasion
that taught it, in parentheses. Rules inferred from the author's own edits (not stated) start with
`Inferred:`. Add a rule in the same turn as the correction (`taste add`).

## Definitions and terms

## Structure
- Related Work goes after the Discussion, just before the Conclusion, so it can contrast prior work with our findings. (Q1.1)
- Each topic (e.g. project size and growth) is discussed at a single location; other sections point to it instead of restating it. (RQ5 corpus paragraph vs Code Growth results)
- Implications subsections: one idea per paragraph, each opened by a \textbf{...} header naming it. (Discussion, implications subsections)
- Inferred: Results subtopics of an RQ are \subsubsection, not \paragraph. (RQ5 results, author turned paragraphs into subsubsections)

## Method
- Drop cliché SE metrics (e.g. cyclomatic complexity) that say nothing new about the studied phenomenon, even when they yield a result. (RQ5 quality metrics)

## Style
- State the measured value (median, min, max) instead of a rounded paraphrase such as 'about three months' or 'two-thousand-fold'. (RQ5 corpus paragraph, observation span)
- Inferred: Paragraph headers are the shortest noun phrase naming the topic ('Code quality', not 'Code quality measurements'). (RQ5 method, paragraph header renamed by author)
- End a non-significant result on a positive recommendation (what to watch), not on a 'remains a hypothesis, would need more data' disclaimer. (RQ5 duplication paragraph)
- Remove text that names no concrete metric or number, and any figure that only repeats a table. (RQ5 slope-distribution paragraph and figure)
